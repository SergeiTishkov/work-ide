# Как искать названия технологий в тексте вакансии

Документ общий, для всех пользователей проекта. Он о механике поиска, а не о
чьём-то конкретном стеке: что в вакансии написано `.NET`, `C++` или `Go`,
одинаково верно для любой идентичности.

Читать обязательно перед тем, как добавлять технологию в стек идентичности
или чинить «фильтр что-то не находит».

---

## Главное правило

> Совпадение подстрокой — поведение по умолчанию, и оно ошибается тихо.

Ложное срабатывание видно: в отчёте появляется лишняя строка, человек её
читает и ругается. Ложный **пропуск** не виден никому: вакансия просто не
приходит, и никто не знает, что она была. Поэтому пропуски дороже, и искать
их нужно замерами, а не ожиданием жалобы.

Самая дорогая ошибка в истории проекта была именно пропуском — см. ниже.

---

## Случай `.NET`: как одна строчка спрятала 754 вакансии

**Симптом.** Владелец спросил: «дотнет — популярная платформа, работы много,
почему её нет в выдаче?» Замер 2026-08-05 по базе из 11 414 вакансий:

| | |
|---|---|
| `.NET` в заголовке | 754 |
| прошли в выдачу | **0** |
| отклонены с формулировкой «не .NET/JS роль» | **325** |

То есть дотнет-вакансия отклонялась за то, что она не дотнет.

**Причина.** Голого `.NET` не было ни в одном списке ключей. Были только
формы длиннее: `.NET Core`, `.NET Framework`, `ASP.NET`, `C#`. Заголовок
«Senior .NET Backend Developer» не содержит ни одной из них:

```
normalize("Senior .NET Backend Developer") = "senior .net backend developer"
   содержит ".net core"      -> нет
   содержит ".net framework" -> нет
   содержит "asp.net"        -> нет
   содержит "c#"             -> нет
```

**Почему не добавили просто `.net`.** Потому что подстрока `.net` есть в
каждом почтовом домене и в каждой ссылке. В базе лежит реальная запись с
Hacker News, приехавшая заголовком вакансии:

```
Please email me so I know which role ... (firstname)@harnly.net
```

Добавь `.net` в список ключей — и такие записи станут дотнет-вакансиями.

---

## Решение из двух частей

Обе части обязательны. Первая без второй не работает, вторая без первой
опасна.

### 1. Почта и ссылки вырезаются ДО поиска

`tools/textclean.py`. Каждое слово текста проверяется отдельно; слово,
похожее на почтовый адрес или ссылку, заменяется пробелом.

**Это не валидация адреса, а распознавание формы.** Разница принципиальна, и
она проверена на живых данных:

* `email.utils.parseaddr` из стандартной библиотеки **не распознал**
  `(firstname)@harnly.net` — ту самую запись, ради которой всё затевалось:
  скобки трактуются как RFC-комментарий, локальная часть выходит пустой;
* `email-validator` (тот, что внутри Pydantic) отверг бы её тем более: он
  проверяет, что адрес настоящий и доставляемый, а `(firstname)` — шаблон.

Нам нужен ответ не на вопрос «можно ли сюда написать письмо», а на вопрос
«похоже ли это слово на почту настолько, что искать в нём технологию
бессмысленно». Валидатор отвечает на первый и потому раз за разом ошибается
на втором: всё нестандартное — шаблоны, огрызки, адреса с опечатками — он
объявляет не-почтой, и `.net` из них снова попадает в поиск.

Граница осторожности: убираются только однозначные случаи — слово с `@` в
форме адреса и слово со схемой (`http://`, `https://`) или с `www.`. Голый
домен `harnly.net` без `@` и без схемы **не трогается**: он неотличим от
`asp.net`, а цена ошибки несимметрична.

Проверить руками:

```bash
python tools/textclean.py --show "пишите на jobs@example.net про asp.net"
python tools/textclean.py "пишите на jobs@example.net про asp.net"
```

### 2. Технология ищется регуляркой, а не подстрокой

`config/tech_vocabulary.yaml`, раздел `matching_patterns`:

```yaml
matching_patterns:
  ".NET":
    substring_unsafe: true
    patterns:
      - '\.net\b'
      - '\bdotnet\b'
    redundant_if: [".NET Core", ".NET Framework", "ASP.NET", "ASP.NET Core"]
```

Три поля, и каждое закрывает свою ошибку:

| поле | что случится без него |
|---|---|
| `patterns` | `.NET` не найдётся вообще (исходный баг) |
| `substring_unsafe` | `.NET` начнёт находиться внутри `asp.net` — тот же баг наоборот |
| `redundant_if` | одна платформа посчитается дважды: и как `ASP.NET`, и как `.NET` |

---

## Почему это лежит в `config/`, а не в идентичности

По CLAUDE.md §13. Проверочный вопрос: «стало бы лучше любому, кто склонирует
репозиторий?» Как пишется `.NET` в тексте вакансии — факт о мире, одинаковый
для всех. Является ли `.NET` ядром чьего-то стека — факт о человеке.

Поэтому:

* **идентичность** называет технологию каноническим именем в своём
  `tech_stack` — и получает правильный поиск бесплатно;
* **идентичность не хранит регулярок вообще.** Это проверяется тестом
  `test_dotnet_pattern_lives_in_the_global_vocabulary_not_in_identities`.

Первая редакция этого исправления положила регулярки в
`kisel_profile.yaml` — то есть в слой одного человека. Ошибка слоя: у
владельца и его друзей дотнет общий, и каждая новая идентичность начинала бы
с того же бага.

## Правило для коротких и общих слов

Куплено опытом, повторять не нужно. Уже ловились:

| ключ | ложно совпадал внутри | цена |
|---|---|---|
| `ssis` | `ai-assisted` | 1057 срабатываний, вакансия без SSIS вышла на 1-е место |
| `ssas` | португальское `nossas` | вакансии не на том языке |
| `java` | `javascript` | Java-гейт не срабатывал вообще |
| `.net` | `harnly.net`, `asp.net` | 754 вакансии |
| `LESS` | `no less than` | ложный стек |
| `eor` | `theoretical` | ложный сигнал найма |
| `G-P` | `Mentoring-Programm` | ложный EOR |
| `expo` | `exposure`, `export` | ложная мобильная разработка |

Отсюда правила для `technologies` в словаре:

* формы короче 4 символов — только с уточнением (`.net core`, не `.net`);
* акронимы — полностью (`sql server integration services`, не `ssis`);
* названия-омонимы — с суффиксом (`.js`, ` framework`, ` language`);
* если ни один вариант не безопасен — технология переезжает в
  `matching_patterns` и получает регулярку.

## Чек-лист: добавляю технологию в стек

1. Написать все формы, какими её называют в вакансиях.
2. Для каждой спросить: **является ли она подстрокой обычного слова или
   другого названия?** Проверить не в уме, а замером по базе:

   ```bash
   python - <<'PY'
   import json, sys; sys.path.insert(0, "tools")
   import common; common.activate_identity("<префикс>")
   v = json.load(open(common.VACANCIES_PATH, encoding="utf-8"))
   needle = "<форма>"
   hits = [r for r in v.values()
           if needle in common.normalize_for_matching(
               (r.get("title") or "") + " " + (r.get("description_text") or ""))]
   print(len(hits), "совпадений")
   for r in hits[:15]:
       print("  ", r["title"][:70])
   PY
   ```

   Глазами по списку сразу видно, ловится ли слово внутри чужого.
3. Безопасна — в `technologies`. Небезопасна — в `matching_patterns` с
   `substring_unsafe: true`.
4. Если название вложено в другое (`.NET` внутри `ASP.NET`) — заполнить
   `redundant_if`.
5. Написать тест на реальной строке из базы, а не на выдуманной.

## Как заметить такую дыру, не дожидаясь жалобы

Замер, который нашёл случай `.NET`, стоит повторять при каждом заметном
изменении фильтров. Идея простая: **взять технологию, посчитать её вакансии
в базе и посмотреть, сколько дошло до выдачи.** Ноль из сотен — это всегда
повод разбираться, даже если объяснение «такой рынок» звучит правдоподобно.

Особенно если объяснение звучит правдоподобно: рынком легко объяснить
что угодно, и это ровно та ошибка, которую здесь уже допустили один раз.
