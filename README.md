# Work IDE

Автономная система поиска работы, управляемая AI-агентом. Вы описываете, какую
работу ищете, — система постоянно собирает вакансии из открытых источников,
отсеивает заведомо неподходящие, ранжирует остальные и выдаёт отчёт, который
читается за десять минут.

## Почему «Work IDE»

**Work IDE = work identity.** Название читается как «IDE» — среда разработки, — и
это уместная игра слов: перед вами действительно рабочая среда, только не для
кода, а для поиска работы. Но расшифровывается оно иначе, и расшифровка важнее
каламбура.

**Идентичность** — центральная сущность проекта. Это один явный объект,
отвечающий на вопрос «кто ищет и что именно»: стек, формат занятости, гео,
языки, зарплатные ожидания, целевые компании и рубрика оценки. Не россыпь
настроек по файлам, которую нужно держать в голове, а одна папка, которую можно
открыть, прочитать, скопировать целиком или выбросить.

Из этого следует всё остальное, ради чего проект так назван:

- **Настроить фильтры просто.** Не «поправьте семь конфигов в разных местах», а
  «ответьте на девять вопросов — агент соберёт идентичность». Гео- и языковые
  фильтры при этом **выводятся** из ваших ответов, а не переписываются вручную:
  фраза «US only» для резидента США — плюс, для всех остальных —
  дисквалификация, и решать это должна машина, а не ваша память.
- **Поисков может быть несколько, и они не мешают друг другу.** Спокойная
  малозагруженная работа и амбициозная полная ставка — противоположные критерии,
  в одной рубрике их не выразить. Это две идентичности, у каждой своя база
  вакансий и свой отчёт. Радиус поражения любой правки равен одной папке.
- **Данные разных людей не смешиваются.** Не по договорённости, а по устройству:
  без активной идентичности инструменты просто отказываются работать. Смешение
  даёт правдоподобный, но неверный результат — то есть отказ, которого никто не
  заметит, а такие дороже всего.
- **Своим поиском можно поделиться, не делясь собой.** В репозитории лежат
  **шаблоны** идентичностей — типы поиска без единого личного факта. Вы клонируете
  шаблон себе, и ваша копия с резидентством, зарплатой и CV остаётся вне гита.

Пользоваться проектом предполагается через AI-агента (Claude Code и подобные),
а не набирая команды руками. Поэтому документация написана в первую очередь для
агента — он здесь и разработчик, и среда исполнения. Идентичность — то, что
превращает агента общего назначения в агента, знающего именно ваш поиск.

## С чего начать

**Если вы первый раз:** откройте проект в агентской среде и скажите что-то вроде
«хочу настроить поиск работы под себя». Агент проведёт вас по
[docs/ONBOARDING.md](docs/ONBOARDING.md): спросит про ваш опыт (CV, LinkedIn или
просто рассказ), покажет готовые шаблоны поиска, склонирует подходящий вам и
заполнит вместе с вами личную часть.

**Без идентичности поиск не работает** — это не ограничение, а защита: смешение
данных двух людей даёт правдоподобный, но неверный результат, который никто не
заметит.

**Идентичностей может быть несколько**, в том числе у одного человека: спокойная
малозагруженная работа и амбициозная полная ставка — противоположные критерии, в
одной рубрике их не выразить. Добавить новую можно в любой момент, уже настроенный поиск от этого не
пострадает — см. [docs/ONBOARDING.md](docs/ONBOARDING.md), раздел «Вторая и
последующие идентичности».

### Установка

Нужен Python 3.9+ и три библиотеки. Больше ничего: ни ключей API, ни платных
подписок, ни внешних сервисов.

```bash
git clone <repo> && cd work-ide
python -m venv .venv
```

Активация окружения зависит от системы:

| Система | Команда |
|---|---|
| macOS / Linux | `source .venv/bin/activate` |
| Windows (PowerShell) | `.venv\Scripts\Activate.ps1` |
| Windows (cmd) | `.venv\Scripts\activate.bat` |

```bash
python -m pip install -r requirements.txt
python -m pytest -q          # необязательно, но покажет, что всё цело
```

Дальше скажите агенту «хочу настроить поиск работы» — он проведёт онбординг.

### После онбординга

```bash
python tools/identity.py which     # какая идентичность активна
python tools/doctor.py             # всё ли в порядке
python tools/pipeline.py           # цикл поиска
```

**До онбординга эти команды намеренно отказывают** — идентичности ещё нет, а
искать «за кого-нибудь» система не станет. Отказ объясняет, что делать дальше.

Результат — `reports/<префикс>_latest.md`. Папка `reports/` лежит в корне
репозитория: отчёт открывают руками, и искать его в дереве накопленных данных
неудобно. Её нет в гите и нет в свежем клоне — инструменты создают её сами при
первом прогоне.

## Как это работает

1. **Сбор.** Несколько источников без авторизации: агрегаторы удалённых вакансий
   (WeWorkRemotely, RemoteOK, Remotive, Jobicy, Himalayas), карьерные страницы
   компаний напрямую через их ATS (Greenhouse, Lever, Ashby, Recruitee), тред
   Hacker News «Who is hiring». Плюс ручной канал: агент ищет обычным веб-поиском
   там, куда скриптам ходить нельзя, и заносит находки.
2. **Жёсткие фильтры.** Всё заведомо невозможное отсеивается полностью: не та
   локация, не тот язык, не та профессия, не тот стек. Это гейты, а не штрафы в
   баллах — иначе непроходное всплывает в выдаче за счёт общих слов.
3. **Оценка.** Прошедшее ранжируется по прозрачной рубрике, у каждой вакансии
   видна раскладка балла по компонентам.
4. **Обогащение.** Проверка живости ссылок, возраст компании из Wikidata,
   репутация работодателя и вилка зарплаты. Площадки с отзывами закрыты для
   скриптов, поэтому рейтинги ищет агент — но СПИСОК того, что осталось
   проверить, система составляет сама и жалуется, пока он не пуст. У каждой
   компании головы выдачи есть результат: либо оценки, либо честное
   «искали и достоверных отзывов не нашли».
5. **Отчёт.** Кандидаты по классам, с зарплатой и **явным указанием её
   источника**, ссылкой на сайт компании для отклика напрямую и репутацией.

Автоматика — только первый фильтр. Перед тем как считать вакансию находкой,
агент обязан прочитать её целиком и пройти
[docs/VACANCY_CHECKLIST.md](docs/VACANCY_CHECKLIST.md): keyword-скоринг находит
только то, что кто-то заранее внёс в список, а формулировки в объявлениях
бесконечно разнообразны.

## Структура

Граница проходит по гиту: слева — общее и обезличенное, справа — ваше.

```
CLAUDE.md              Большая Конституция: принципы, общие для всех
RUNBOOK.md             что выполнять в каждом цикле поиска

identity-templates/    ТИПЫ поиска. В гите. Ни одного личного факта.
  README.md              как клонировать, правила именования
  blank-.../             пустая заготовка, если не подходит ни один готовый
  <префикс>-<расшифровка>/   папка объясняет себя именем:
    template.yaml            номер версии шаблона
    CHANGELOG.md             что изменилось, новыми версиями вверх
    <префикс>_profile.yaml   kisel-keep-it-simple-easy-legacy/
    <префикс>_criteria.yaml  а файлы внутри короткие: kisel_profile.yaml

config/                общая машинерия (ничего личного)
  sources.catalog.yaml   какие источники существуют и что умеют
  tech_vocabulary.yaml   как технологии называются в вакансиях
  derivation/            таблицы для вывода гео- и языковых правил
  settings_policy.yaml   что локальный слой менять НЕ может

tools/                 CLI-инструменты, каждый решает одну задачу
docs/                  документация (см. ниже)
.claude/commands/      готовые команды агента: /start, /run, /add-identity…

local-identities/      ВНЕ ГИТА: ВАШИ поиски. Здесь можно всё.
  <префикс>-<расшифровка>/
    identity.yaml          из какого шаблона и какой версии
    template/              дословная копия шаблона — не редактируется
    <префикс>_profile.yaml ваши ОТЛИЧИЯ от шаблона накладываются поверх
    documents/             ваши CV под их собственными именами
    CHANGELOG.md           журнал ваших изменений

reports/               ВНЕ ГИТА: готовые подборки, создаётся автоматически
  <префикс>_latest.md    свежая подборка каждой идентичности — открывать это
  archive/<префикс>/     история: 2026-07-31.md, 2026-08-01.md, …

data/<префикс>/        ВНЕ ГИТА: накопленная база, сырые дампы, состояние
```

**Сколько папок в `local-identities/` — столько подборок делает система.**
Отдельного реестра активных идентичностей нет намеренно: файл со списком умеет
разойтись с тем, что лежит на диске, а папки — нет.

Копия шаблона внутри вашей идентичности — не дубликат по недосмотру. Благодаря
ей `git pull` не может изменить вашу выдачу: шаблон в репозитории обновился, а
ваша копия осталась прежней. Обновление происходит по явному согласию и является
заменой папки `template/`, а не слиянием текстов — ваши настройки лежат отдельно
и потеряться не могут.

## Границы

Проект свободно читает всё, что отдаётся обычным HTTP-запросом, и делает это
вежливо: честный User-Agent с контактом, паузы между запросами, кэширование.

Проект **не обходит** активную защиту от ботов — подделку отпечатка браузера,
CAPTCHA, headless-браузер ради обмана детектора. Площадки, закрытые такой
защитой (Glassdoor, Indeed, LinkedIn), доступны только через агента, который
ищет там как обычный человек и заносит находки вручную. Подробнее и с
замеренными кодами ответов — [docs/SOURCES.md](docs/SOURCES.md).

## Команды агента

Если вы работаете через Claude Code, в проекте есть готовые точки входа:

| Команда | Что делает |
|---|---|
| `/start` | Онбординг: собрать идентичность с нуля и сделать первый прогон |
| `/run` | Обычный цикл поиска, включая обязательную ручную проверку кандидатов |
| `/add-identity` | Добавить ещё один поиск, не сломав уже настроенный |
| `/check` | Самопроверка: окружение, идентичности, источники, тесты |
| `/applied` | Отметить отклик и его результат |

Это тонкие обёртки над документацией, а не её дубль: они гарантируют, что
нужный документ будет прочитан, а обязательные шаги — не пропущены.
